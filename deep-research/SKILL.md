# Deep Research

Работает только по явному вызову `/deep-research`. Вызова не было — выходи сразу и отвечай на вопрос обычным порядком.

## Веб, не память

Каждое содержательное утверждение отчёта берётся из найденного в вебе — обязательно используй WebSearch и WebFetch, не отвечай из обучающих данных. Знание из памяти годится только как гипотеза для формулировки запроса.

Первый заход по теме — WebSearch: ранжирование Google достаёт кураторский экспертный контент (документацию, обзоры, гайдлайны) плотнее прочих источников. Дальше порядок задаёт файл корпуса твоей ветки, и он же решает, с чего начинать дискавери.

## Бриф и роутер

Собери в бриф ограничения из двух источников: сам запрос и `~/.claude/CLAUDE.md` (платформа, стек, язык, страна). Оттуда — факт; всё прочее не досочиняй: условие, которого пользователь не давал (версия, бюджет, конкретная площадка), либо не добавляй, либо явно пометь как своё допущение — не подавай его дальше как требование.

__Сохранённая память — не источник: не читай файлы памяти и не поднимай запомненное из прошлых сессий. Там лежат протухшие и никем не вычищенные утверждения, и попав в бриф, они уводят поиск молча.__

По брифу определи, **какой ответ нужен пользователю**, и прочитай референс этой ветки:

- выбрать из вариантов — «какой NAS взять», «какой библиотекой валидации пользоваться» → `references/choice.md`, он начинается с выбора файла корпуса;
- взвесить доказательства — «вреден ли аспартам», «работает ли креатин» → `references/evidence.md`;
- понять, как что-то устроено или что произошло — «как устроен LSP-сервер», «известен ли этот баг, есть ли обход», «что случилось с этим сервисом», «кто такой этот автор» → своего референса нет, работай по этому файлу; если предмет софтовый, тактики поиска возьми в `references/corpus-software.md`.

Вопрос бывает составным. «Вреден ли синий свет и какие очки с фильтром купить» — это и «взвесить доказательства» (вреден ли), и «выбрать» (какие купить): подгружай референсы обеих веток, не одной.

## Поиск

Запрос к WebSearch: именная группа темы, год при чувствительности к свежести (текущий — из `# currentDate` системного контекста), уточнитель — локация, язык, аудитория. Итерируй, пока каждая новая выдача даёт новое.

Скрипты `search-reddit`, `search-hn`, `search-github` лежат на `$PATH` и поддерживают `--help` и `--json`; команды, тактики и очерёдность — в файле корпуса: софт — `references/corpus-software.md`, товары и услуги — `references/corpus-market.md`. Там, где у ветки есть файл корпуса, скрипты обязательны: ощущение, что выдача WebSearch уже полна, — не основание их пропустить, потому что чего он не индексирует, того ты в нём и не увидишь. Без скриптов работают вопросы, у которых корпуса нет вовсе, — например когда взвешиваешь доказательства.

## Гигиена запросов

Пустой результат — факт о твоём запросе, не о мире. Свидетельством отсутствия он становится только после того, как исключён сам запрос.

- **Упавший вызов — не результат.** Ненулевой exit, `gh error:`, TLS-ошибка, `IncompleteRead` → перезапусти; с `dangerouslyDisableSandbox: true`, если замешан сандбокс. Упавший вызов не засчитывается в покрытие.
- **Пустая выдача отфильтрованного или длинного запроса — не доказательство отсутствия.** Перезапусти короче и без фильтров, прежде чем заключать.
- **Один негативный ответ не закрывает шаг.** Один ракурс запроса, вернувший пусто, отменяет этот ракурс, а не весь канал: заходи с другой стороны, прежде чем вычёркивать источник.
- **Отсутствие — вывод, который надо заработать.** «Публичных репортов нет», «никто это не мерил», «в местных сабах не обсуждают» пиши только после ≥2 разных заходов; иначе это отчёт о собственном поиске, а не о мире.

## Синтез

Противоречия источников сталкивай явно, не сглаживай, и взвешивай по силе: официальный документ и первоисточник весят больше названного эксперта, тот — больше треда сообщества, тред — больше анонимного блога. Утверждение с единственным источником помечай как одиночное.

## Нота в vault

Если у пользователя есть Obsidian vault, каждый прогон заканчивается сохранением отчёта нотой `type: deep-research` — не спрашивая.

Конвенции vault — в скиле `obsidian-vault`: размещение, именование, схема frontmatter (`_types/deep-research.type`), связи только во frontmatter. Поверх них:

- `status: current`, `date` — сегодня из `# currentDate`;
- слаг: добавь `-<год>`, если тема чувствительна к свежести;
- тело — синтез; секция `## Источники` со внешними URL обязательна;
- 1–3 реальных ссылки в `linked:`; если напрашивается хаб области — впиши ноту и туда.

После записи покажи отчёт в чате с кликабельным путём ноты.

## Смок-тест каналов — выполняется до первого содержательного запроса

Проверь ровно те каналы, которыми собираешься работать в этом прогоне. Ветка доказательств идёт на WebSearch и WebFetch — скрипты и `gh` ей не нужны, и тестировать их незачем. Скрипты проверяй только если подгрузил файл корпуса, `gh` — только если собираешься читать README awesome-списка.

Проверка — минимальным реальным вызовом, а не `--help`: он подтверждает лишь то, что файл читается, а отваливаются чаще сеть, права и песочница.

```bash
search-reddit search "test" --limit 1
search-hn search "test" --limit 1
search-github search "test"        # dangerouslyDisableSandbox: true
gh api rate_limit                  # dangerouslyDisableSandbox: true — сеть, TLS и живой токен разом
```

`gh` проверяется отдельно от `search-github`: чтение README идёт прямым `gh api`, и протухший токен или TLS кладут этот шаг, когда скрипт-обёртка ещё отвечает.

**Нужный тебе канал не отвечает — ресёрч не начинай.** Остановись, напиши пользователю, что именно сломано, что ты пробовал и какая часть покрытия выпадает, и жди решения. Продолжай только по прямому «гони как есть» — и тогда назови выпавший канал в самом отчёте, рядом с выводами, которых он касается.

Заметить поломку и всё равно догнать прогон до конца — худший исход: отчёт выглядит полным, а дыры в покрытии не видно ни тебе, ни пользователю.
