## Задача

Актуализировать указанный скоуп документации (таску, док, регион, связку доков фичи): найти все несоответствия действительности, все внутренние ошибки и противоречия, и разрешить их.

Источник истины всегда реальность, которую читаешь сам: код, конфиги, git включая WIP, timeline задач. Замыслу не доверяй как описанию сделанного: ТЗ задачи, roadmap, target-под-доки genesis описывают намерение, с которым реализация разъехалась (implemented ≠ done). Самим current-state докам тоже: они предмет проверки, ими нельзя подтверждать их же правоту.

Работа идёт в две фазы через нативный plan mode. Фаза эксплоринга ёмкая по контексту и read-only: она находит, диагностирует и предлагает; все решения фиксируются планом на апруве. Фаза исполнения чувствительная и механическая: она делает ровно то, что апрувнуто, не передумывая.

## База: /extract обязателен

Этот скил только дельта поверх `/extract`. Если `/extract` ещё не загружен в контекст сессии, вызови его через Skill tool **прямо сейчас, до любых действий**: пайплайн записи, гарды и таблица роутинга живут там.

## Фаза 1: эксплоринг и план

1. **Подними недоведённую работу.** Git и код не покажут правду, висящую в брошенных сессиях. Когда скоуп широкий или регион давно без коммитов (полная актуализация региона подпадает почти всегда), прогони `/state-reconstruction`, дай пользователю дозакрыть сессии и только потом иди дальше: детекция по неполной картине даёт ложные находки. Пропускай только при точечном скоупе с уверенным «WIP нет» от пользователя.
2. **Войди в plan mode** сам (`EnterPlanMode`) и прочитай скоуп целиком, ничего не правя; границу держи по связям, а не по папке. Ищи расхождения двумя способами одновременно:
   - **дрейф**: сверяй current-state доки с системами, которые они описывают (код, конфиги, git);
   - **противоречия**: от каждой находки иди по связям волной, к связанным докам, от них к их связанным, пока новые не перестанут противоречить; волна может уйти за исходный скоуп, иди за ней.
3. **Диагностируй каждую находку и предложи резолюцию.** Это и есть содержимое будущего плана:
   - устарело или изначально ошибочно зафиксировано: резолюция «починить по реальности», распиши, что на что меняется;
   - ответ лежит вне досягаемости агента (физический мир, намерения, приоритеты): развилка с вариантами, решит пользователь на апруве;
   - непродуманность (изменение внесли, а влияние на другую часть системы упустили): не правка дока, а «зафиксировать open-question / task»: противоречие честно отражает дыру в дизайне;
   - находки фиксируй только по current-state и knowledge докам, они претендуют на «как есть». Analysis / seed (idea, problem) читай как контекст: внутренняя разведка (взвешенные варианты, отвергнутый путь) не находка; фактическое устаревание находка и там, с резолюцией «lifecycle-ход»: analysis актуализировать / завершить concluded / выпустить в spec или decision, у seed сдвинуть статус, тело не трогать;
   - **разъехавшиеся роли — находка.** Интент эффорт-цепочки, вписанный первой секцией в тело analysis / task / спеки вместо отдельного seed, — hygiene violation с резолюцией «выпустить в seed» (если роль не занята upstream). `incident`, в тело которого смерджена fault-line вместо линка на `problem`, — тоже: occurrence закрывается, фолт живёт дальше, склейка эту раздельность теряет. `problem`, разросшийся в эпопею symptom + расследование + фикс, разносится по ролям (`analysis kind: investigation`, `task`, `knowledge`). Повторяющаяся обязанность, живущая одноразовой задачей или проектом со статусом-хаком, — находка с резолюцией «завести routine»;
   - implemented-таска в скоупе разворачивается в свои пункты плана: догнать спеки по `kind` (feature: business + implementation; bugfix: только implementation, код вернулся к неизменной business-spec; refactor: только implementation), выпустить genesis-под-доки spec-draft в самостоятельные спеки, сверенные с кодом, decision на значимый разрыв замысла с реальностью, заморозить task в `done` целиком (коммиты, acceptance, timeline не расплющивать), закрыть разрешённые open-question (`resolved` / `dropped`);
   - напрашивающийся структурный ход (расщепить, перенести, ретипизировать) предлагай пунктом плана, обязанности искать их нет; полная пересборка раскладки не сюда, это `/rewrite`. Ход, вводящий новый тип или подтип, проверяй правилом подкатегоризации из conventions-скила (schema-divergence delta: другой lifecycle / шаблон / field-set → подтип через `extends:`, иначе значение `kind:`) — «завести отдельный тип» без этого теста находкой не считается.
4. **Предъяви план** (`ExitPlanMode`): список находок чекбоксами, по строке на находку: `- [ ] док: что не так, диагноз, резолюция`. Развилки с вариантами прямо в плане: план и есть батч вопросов пользователю, по одному не спрашивай. Пользователь правит план и апрувит.

## Фаза 2: исполнение и сверка

5. **Исполняй план буквально**, находку за находкой, отмечая закрытые в план-файле (`~/.claude/plans/*.md`): `- [x]`. Решения приняты на апруве, не передумывай их. Вскрывшееся по ходу новое добавляй в план отдельными пунктами; новые вопросы собирай батчем, а не задавай по одному.
6. **Сверься с планом.** Пройди чекбоксы построчно: каждый закрыт или явно отложен с причиной.
7. **Финал** обычный для `/extract`: проверка, линтеры, коммит шагами. Если дальше планируется `/rewrite` региона, заверши через `/handoff-create` с дистиллятом: какие ошибки сняты, какие противоречия в чью пользу решены, диапазон коммитов; детали давай ссылкой на коммиты, а не пересказом.
