Разложить вывод сессии по типизированным артефактам, переписать current-state доки под реальность, удержать связанные доки согласованными и закоммитить. Конкретные типы, папки и как заводится документ — из conventions-скила хранилища (шаг 1); их «что и когда» — ниже.

## Тип определяет, несёт ли док время

От этого зависит, применяются ли гарды — они держат чистыми только current-state-снимки.

- **current-state** — `business-spec` (что система делает) / `implementation-spec` (как построена). Снимок настоящего: без истории и статусов, переписывается под актуальное. **Только к ним применяются гарды** (ниже).
- **process** — `seed` (`idea` / `problem`) / `analysis` / `task` / `open-question`: сама работа, текущая из будущего в прошлое; время несёт `status:` / `timeline:`.
- **event** — `decision` и `event` с подтипами `meeting` / `incident`: authored-запись о случившемся, **не переписывается**.
- **recurring** — `routine`: родитель-серия повторяющегося усилия, порождает occurrences и сама не завершается.
- **knowledge** — как пользоваться; evergreen.

## Процедура

1. **Прочитай конвенции контекста.** Вызови conventions-скил этого хранилища — `/obsidian-vault`, `/senate-vault` или docs-скил репо. Он даёт surface (как роль кодируется в `type:`/папку, где лежит тип, как создаётся/мутируется документ — CRUD-тулинг, если есть; иначе пишешь файл по конвенции: frontmatter, kebab-slug, папка типа, даты не угадывай — бери из системы), **рецепты поиска** и **валидатор**, если он у контекста есть. Форма ссылок и их проверка — тоже его: у каждого хранилища свой синтаксис (wikilink / относительный markdown / MDX), в движке он не зашит. Детект контекста (senate / личный vault / dev-репо) выводи из сессии.
2. **Классифицируй** вывод сессии на units. У каждого — одна роль (см. таблицу). Роль определяет тип; граница близких типов (business-spec ↔ implementation-spec, idea ↔ open-question, analysis ↔ спека) — `references/types.md`. Если роль не покрыта существующим типом и напрашивается новый тип или подтип — не решай ad-hoc: применяй правило подкатегоризации из conventions-скила (тест schema-divergence delta: расхождение в lifecycle / шаблоне / field-set → подтип через `extends:`; иначе — значение `kind:` внутри существующего типа).
3. **Найди и проверь связанное.** Не предполагай, что знаешь, где целевой док и есть ли он вообще. До роутинга найди всё, что относится к каждому unit — по имени, содержимому, бэклинкам, `type:`+осям (`feature` / `parent`), — прочитай кандидатов целиком и **проверь на предмет**: внутренних противоречий, ошибок, устаревшего/неактуального, расхождения с реальностью (код / конфиг / git), битых ссылок, пробелов. Три цели: не плодить дубли (апдейт существующего, не второй док); поднять доки, которые эта работа рассогласовала; **починить найденное** — не только целевой док, но и смежные, тем же прогоном по гардам (Гард 4 — не бойся переписать целиком). Аудит на корректность — не боковая проверка, а ядро: затронутый регион должен остаться согласованным.
4. **Роутинг.** Каждый unit → найденный существующий док на апдейт, либо новый тип по таблице, если подходящего нет (Гард 3: не сваливай разнородное в один док). Размещение: артефакты эффорта с живым проектом колоцируются в папке проекта по типовым подпапкам (`ideas/` / `analysis/` / `tasks/` / `business-spec/` / `implementation-spec/` / `decisions/`), а не в глобальных папках типов — location-warning валидатора при этом ожидаем (decision `effort-artifacts-colocated-in-project`). Внутри типовой подпапки допустим **ровно один уровень** тематических подпапок (`implementation-spec/git-commit/…`), глубже не вкладывать: это временная замена разделению через поля (`feature`, derived views) — когда оно появится, папки схлопнутся.
5. **Применяй** — к целевому доку и к каждому, что поднял аудит. НЕ append: перечитай док целиком, переосмысли, перепиши на месте чистым current-state-снимком (create / update по конвенции). Перенос между доками — явный шаг.
6. **Гарды** (ниже) — на каждой записи в current-state док.
7. **Проверь.** Записанное читается само по себе, без контекста сессии. Аудит (шаг 3) закрыт: связанные доки согласованы, расхождений с реальностью не осталось. Прогнал FM1-линтер и валидатор контекста (ссылки и раскладка — им, не глазами).
8. **Коммит** — вшит финальным шагом: `git-commit-atomic -C <repo> --auto -S "<msg>" <правленые файлы>` (позиционно — не загребай чужое dirty).

**Вставленные скрины.** Если в сессии есть картинки, вставленные в чат и релевантные тому, что фиксируешь (баг-репорт, скрин ошибки), — это не файлы, а base64 в транскрипте: достань их скриптом `extract-images` (механизм — глобальный `AGENTS.md`) и размести как asset по asset-конвенции контекста (шаг 1 даёт её вместе с surface — `/obsidian-vault`, `/senate-vault` и т.п.), встроив embed-ссылку в док. Не хардкодь пути: раскладка assets у каждого хранилища своя.

## Таблица роутинга (роль → тип)

| Вывод сессии | Тип |
|---|---|
| Что система делает сейчас (домен, intent) | переписать в **business-spec** на месте |
| Как система построена сейчас (код / инфра) | переписать в **implementation-spec** на месте |
| Подлинный разворот / отвергнутая альтернатива + причина | **decision** |
| Origin-story (весь путь, почему так пришли) | **analysis** (`concluded`) |
| Нерешённость (развилка / неизвестность / нужен вход) | **open-question** |
| Предложение «надо бы X» — additive intent эффорт-цепочки | **idea** |
| Зафиксированный фолт «нечто сломано» — corrective intent | **problem** |
| Разбор, почему фолт происходит | **analysis** `kind: investigation` (рядом с problem, не внутри) |
| Переиспользуемый обход / понимание | **knowledge** (выпускается из problem) |
| Сбой, случившийся во времени (окно, impact) | **incident**, линкующий `problem` полем `problem:` |
| Нейтральное событие: встреча, поездка, приём | **event** (подтип `meeting`, если плановая встреча) |
| Повторяющаяся обязанность с работой | **routine** + первая occurrence, не одноразовая task |
| План / шаги | **task** |
| Хроника (что, когда сделано) | `timeline:` соответствующей `task` (отдельного лога нет) |
| Решённый open-Q / устаревший снимок | **удалить** (история в git) |
| Сама завершённая работа | **заморозить** (`done` / `concluded`) — не удалять, не расплющивать |

## Гарды

Срабатывают при правке любого **current-state** дока (`business-spec` / `implementation-spec`). Распознать роль дока — обязательный первый шаг: иначе Гард 1 либо пропустит историю в спеке, либо снесёт законную хронику в process-доке.

**Гард 1 — нет истории в спеке.** Спека — «что ЕСТЬ», без временной шкалы. Разворотный язык — баг: `раньше`, `прежн…`, `было ошибкой`, `пересмотрено`, `убрано`, разворотное `теперь`, `было X стало Y`. Дельту и её причину разноси (таблица), не держи в спеке. После правки:

```
bun ~/.claude/skills/extract/scripts/history-lint.ts <правленый файл или папка>
```

Маркеры детерминированы; линтер пропускает history-роли (`analysis`/`task`/`idea`/`open-question`/`decision`/`incident`) и fenced-код. Доверяй; вычищай каждое срабатывание в current-state доке.

**Гард 2 — пропорция и альтитуда.** Масштаб правки соразмеряй со значимостью изменения **для всей системы**, а не с тем, сколько места оно заняло в чате. Перекос систематичен в одну сторону: раздуваешь то, чем забит контекст, — чаще ошибка в том, что мелкое изменение разбухает до полдока; но по-настоящему крупное заслуживает крупной правки. Альтитуда: правка вливается на той же высоте детализации, что окружающий док (без UI-подписей и пошаговости в высокоуровневом доке). Новый раздел — только под новое *понятие*, не под реализацию. Не задетые разделы не трогай.

**Гард 3 — один артефакт, одна роль.** = таблица роутинга выше. Не сваливай разнородное в спеку — декомпозируй по ролям и разнеси. Три случая, где дефолт агента ломает это чаще всего:

- **Intent-роль.** Если работа породила `analysis` / `task` / спеку, её триггер обязан читаться отдельным артефактом (`idea` для additive, `problem` для corrective). Встретил интент, вписанный первой секцией в тело analysis, — выпусти его в отдельный seed. Роль уже может быть занята upstream (originating-seed рутины, rationale спеки, контекст decision, upstream-task) — тогда дубль не заводится.
- **Фолт.** Не пиши эпопею одним `problem`-доком: фолт → `problem`, разбор причины → `analysis kind: investigation`, фикс → `task`, переиспользуемый обход → `knowledge`, манифестация во времени → `incident` с линком на `problem`. `problem` заводится на любой фолт независимо от владения источником; ownership-разрез решает только, бывает ли следом `task`: по своему коду бывает, по чужому тулу или среде не бывает вовсе — там цепочка кончается обходом.
- **Повторяемость.** Регулярная обязанность — это `routine` плюс occurrence, а не одноразовая `task` и не project со статусом-хаком. Occurrence всегда типизированный файл, не inline-чекбокс.

**Гард 4 — переписывай начисто, не латай.** Несколько точечных правок подряд (особенно разными сессиями) рвут файл: структура уходит, копятся повторы и нестыковки. Как только видишь, что файл дошёл до этого, — бросай латание, прочитай целиком, перепиши как один связный снимок (это переоформление, не добавление объёма — Гард 2 держится). Единственное исключение из «не задетые разделы не трогай». Если файл накопил несколько разъезжающихся концернов (признак — **>500 строк**) — разбей на доки по ролям/темам, не переписывай в один разбухший.

**Гард 5 — `implementation-spec`: невидимое из кода, не пересказ.** Спека держит только то, чего из кода не видно: инвариант, кросс-репный контракт, неочевидное «почему», граблю («сделаешь X → сломается Y»), схему БД, инфру, тест-канон. НЕ пересказ кода — карта файлов, сигнатуры хуков/пропсов, разводка компонентов, «X лежит в файле Y», пошаговая сборка: код скажет это точнее и протухнет на первом же переименовании. Тест по строке: узнал бы это, открыв файл, — режь. Решение со своим `decision` — ссылкой, не пересказом; общий контракт (напр. сериализация параметров api-client'ом) — в спеке своего слоя, не тут. Итог законно усыхает до горсти пунктов или до нуля — тогда спеки по этой работе нет, и это правильный исход, а не недоработка.
