# /state-reconstruction

Скил поднимает всю незафиксированную работу по региону: какие сессии Claude Code его трогали, какие их правки так и не дошли до коммитов, какой WIP висит в git и какие сессии стоит дозакрыть. Регион задаёт пользователь: репо, vault-папка проекта или их связка. Результат: отчёт по шаблону ниже, включая список команд `claude --resume`, по которым пользователь сам заходит в недоведённые сессии. Прогон read-only, регион не правится.

Два правила на весь прогон:

- Каждое утверждение о состоянии бери из команды этого прогона, не из памяти транскриптов.
- Регион кодируй 1-3 подстроками пути (имя папки репо, имя vault-папки проекта). Подстроки матчат и `file_path` тулов, и текст Bash-команд.

## 1. Обратный индекс сессий

```bash
bun ~/.claude/skills/state-reconstruction/scripts/region-sessions.ts <substr> [substr…] [--limit=N]
```

Скрипт сам покрывает и старую историю, и свежие сессии; подготовка не нужна, запускай как есть. Секции вывода:

- `Sessions`: все сессии, трогавшие регион, из любого проекта, со счётчиками edits/writes/reads/bash. Сначала идут сессии, читавшие или правившие файлы региона. Хвост из строк, где заполнен только bash, почти весь шум: регион упомянут в тексте команды (commit-message, find), а не правился. Свою текущую сессию игнорируй.
- `Files`: какие файлы региона правились, какая сессия правила последней и сколько раз. На шаге 4 эта таблица сопоставляется с `git status`.
- `Handoffs`: handoff-файлы региона, отдельно от контента. Статус из frontmatter: `open` значит работа так и не взята, `consumed` значит подхвачена, `no-frontmatter` значит старый формат и статус надо смотреть руками.
- `Bash touches`: расшифровка колонки bash, по сессии её команда. Здесь ищи файлы, созданные через `mv`/`cp`/heredoc: у таких правок нет `file_path`, в `Files` они не попадают и видны только тут. Остальное в секции шум, отличай по тексту команды.

## 2. Git-WIP

По каждому репо, куда попадают файлы из `Files`:

```bash
git-commit-context -C <repo> [-- <paths>]
git -C <repo> stash list
```

`<paths>` передавай, когда регион занимает лишь подпапку репо (vault-проект): без скоупа в выводе окажется весь чужой dirty tree. Со скоупом добавляется секция `LAST COMMIT TOUCHING PATHS` с датой последнего коммита региона; без скоупа возьми её из `git -C <repo> log -1 --format='%h %cI %s'`. `stash list` отдельной командой: в `git-commit-context` его нет.

## 3. Разбор подозрительных сессий

Выбери из `Sessions` 3-8 сессий, чья работа могла не дойти до коммитов:

- сессии с активностью позже последнего коммита региона: после них никто ничего не фиксировал;
- сессии, которые последними правили файлы, грязные сейчас в `git status` (колонка `by session` в `Files`);
- самые крупные по числу правок.

Прогони по ним скрипт session-status:

```bash
bun ~/.claude/skills/session-status/scripts/session-status.ts <uuid> [uuid…]
```

UUID полные, отчёты в выводе разделяются `---`. Все сессии подряд не бери: каждый прогон сканирует весь корпус и стоит дорого.

Скрипт даёт детерминированное: файлы, коммиты, staleness. Нарратив («Что сделано», «Полезное») требует контекста самой сессии; его можно получить, исполнив `/session-status` внутри неё headless:

```bash
claude -p --resume <полный-uuid> "/session-status"
```

Запускай из cwd сессии (колонка `project`), иначе резюм её не найдёт. Это дорогой ход: грузится весь контекст сессии плюс ход модели, поэтому только по самым важным подозреваемым, не по всему шортлисту. Прогон дописывается в JSONL самой сессии (тот же session id): сессия после него уже актуализировала знание о своём состоянии, и при позднейшем интерактивном резюме отчёт будет у неё в истории.

Дешёвый вариант для read-only сессии (много reads, ноль edits, активность позже коммита; session-status по ней пуст, весь вывод остался в чате): вытащить финальный ответ ассистента из JSONL, там план или развилка, которые не легли в артефакты:

```bash
jq -rs 'map(select(.type=="assistant" and (.message.content | type=="array"))) | last.message.content | map(select(.type=="text") | .text) | join("\n")' ~/.claude/projects/<project>/<uuid>.jsonl
```

## 4. Стык: что не легло

- Файл грязный или untracked в `git status`, а его последний редактор виден в `Files`: это незакрытый WIP той сессии.
- Файл правился сессией, но коммита по нему после её окна не было и в `git status` он чистый: работу перетёрли или увезли, проверь куда.
- stash-записи и ветка ahead: незакрытое вне сессий.
- Правки региона позже его последнего коммита: спячка, работа шла без фиксации.

Сессия из первых двух пунктов считается недозакрытой: её работа не легла в артефакты. По каждой собери команду резюма `claude --resume <полный-uuid>`. Перед этим проверь, что JSONL жив: `ls ~/.claude/projects/<project>/<uuid>.jsonl` (ретеншен чистит старые). Мёртвую сессию не предлагай, пометь как «только снапшот». Резюмить нужно из cwd сессии; он закодирован в колонке `project` (`-Users-…` читается как путь).

## Вывод

```
## Реконструкция: <регион>
### Git-WIP
- <репо>: ветка, ahead N, M dirty / K untracked, stash: …
### Незакрытое
- <файл>: <сессия, дата>, <что это и почему не легло>
### Дозакрыть (сессии для claude --resume)
- cd <cwd сессии> && claude --resume <полный-uuid>   # <что довести, 1 строка>
- <uuid>: JSONL умер, только снапшот: <что оттуда вытащить руками>
### Спячка
- последний коммит <дата hash> vs последняя активность сессий <дата>
### Факты только в сессиях
- <команды, цифры, развилки из финальных ответов ассистента и session-status>
```

«Дозакрыть» обязательна, ради неё прогон и делается: пользователь заходит по этим командам сам и доводит сессии до конца. Сессии, по которым гонял headless `/session-status`, уже актуализированы, отчёт лежит у них в истории: резюм сразу доводит работу. По остальным пометь в строке, что первый ход внутри: `/session-status`. Прочие секции, если пусты, пропускай. Этот отчёт — канал детекции недоведённой работы; вход резолюции `/actualize`.

## Escape hatch: сырой SQL

Никогда не агрегируй живой view `msg` по полному глобу: OOM (ловили 14.3 GiB). Два безопасных пути.

По всей истории, через снапшот:

```bash
duckdb ~/.claude/cc.duckdb -readonly -c "SELECT … FROM msg_cache WHERE …"
```

Колонки `msg_cache`: `(project, session_id, ts, text, id)`, без `kind` и `tool`. Tool-блоки лежат сырым JSON, поля тяни через `json_extract_string(text, '$.file_path')`. Фильтруй в `WHERE` до агрегации.

По конкретным сессиям, с настоящими `kind`/`tool`:

```bash
duckdb -init ~/.claude/skills/find-session/assets/cc.sql -c "
ATTACH '$HOME/.claude/cc.duckdb' AS cc (READ_ONLY);
SELECT … FROM msg_src(['<файл>.jsonl', …]) WHERE kind='tool_use' AND …"
```

Список файлов в `msg_src` держи не больше 128 MB на запрос.
